# 上游数据说明

上游是某公共图书馆 OPAC（图创 Interlib 3，Spring Boot + Solr，前置 WAF）。
本项目只使用它对公众开放的只读检索页与只读接口，不做登录、不做借阅。

> 具体的接口路径、参数组合与探测过程**不在本仓库公开**——那部分等于一份现成的抓取指南。
> 维护者本地另有详版笔记；下面只记录**改代码时必须知道的行为约定**。

## 一、字段可信度清单

| 现象 | 真相 | 本项目怎么处理 |
|---|---|---|
| 出版年是 5 位纯数字 | 从 Excel 导入时日期列没转，存成了日期序列号 | 按序列号换算成年份 |
| 出版年像 `2993.7` | 年份首位多敲了一个 2，实为 1993.7 | 4 位年份落在 2900–2999 时减 1000 |
| 「有馆藏」标记为真，但复本列表为空 | 复本可能全落在剔除/不外借库位 | 不反推「馆里没有」，只给说明 |
| 索书号大量为空 | 未编目/临时记录 | 不把索书号排序当可靠排序 |
| 同一馆两个名字（「马尾区图书馆」/「马尾馆」） | 两个接口各给一套 | 一律以分馆代码为准，名称只用于显示 |
| 整页记录都没索书号、都像同一天入库 | **征订层**：订单已导入但书未到馆 | 既不当脏数据删，也不当馆藏报 |

## 二、四条硬约定

1. **「只看可借」只能本地核实。** 上游确实有该筛选参数，但它认的字段和返回的字段对不上，
   筛完反而只剩不可借的记录。所以本项目**不向上游传这个参数**，改为按页拉回后本地核验。
2. **计数与明细必须同源。** 按分馆过滤后若沿用全量计数，会出现「说 4 本、只列 1 条」。
3. **状态/分馆/馆藏地/文献类型是全局字典。** 不同书返回的内容逐字节一致，可以抓一次常驻缓存；
   但**不要写死**，上游随时可能新增状态码。
4. **必填分类检索与复杂条件互斥。** 上游的高级检索表单里没有分类字段，混用会报参数错误——
   这是上游限制，不是本项目的取舍。

## 三、几个容易误判的量级

- **期刊**：单刊可达数百册复本（实测某刊 311 册），必须截断 + 给「按年份分布」。
  卷期字段有两种格式并存（`v.1,no.9,2025` 与 `2026,no.9`），年份和期号要分别用正则抓。
- **新书通报**：编目不是每天更新，90 天窗口全馆可能只有二十几条。**不能据此断定「没有新书」**。
- **排行榜**：馆方定时批处理的产物，未生成时 HTTP 仍是 200，正文是一句提示。
  同一份正文里还夹着分馆清单，任何「递归找第一个对象数组」的兜底逻辑都会把它当榜单。

## 四、只读边界

不涉及登录、借阅、预约、续借；不读取也不存储任何读者个人信息（含读者证号）。
上游有个接口会返回读者证号字段，本项目中**刻意不接入**。

## 五、维护指引

- 上游字段改名：只改 `src/fzlib.js`（领域层），HTTP 细节只在 `src/upstream.js`。
- 全局限流是串行 400ms（`FZLIB_MIN_INTERVAL_MS`）。**想提速就减少请求数，别指望并发**——
  `Promise.all` 在这一层只会排队。
- 复本一律走批量接口一次拿完，别退回「一本一发」。
- 错误码：`UPSTREAM_TIMEOUT` / `UPSTREAM_ERROR` / `UPSTREAM_PARSE_ERROR`（拿到 HTML，
  多半被风控挑战）/ `NOT_FOUND` / `INVALID_PARAM`；可重试的会带 `retryable`。
